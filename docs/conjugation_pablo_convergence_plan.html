Executive decisions

  • Preserve the opt-in production conjugation workflow exactly until a replacement path reaches parity and all consumers of the replaced code are covered. Shared code is deleted only after every dependent path has parity.
  • Use Pablo for topology ingestion of product PDB/connectivity evidence. PolyzyMD remains responsible for reactions, coordinate assembly, charge composition, and OpenFF parameterization.
  • Pin and test Pablo 0.2.2. Use public APIs only: topology_from_pdb(...), ResidueDefinition.from_smiles, from_molecule, from_capped_molecule, react(...), and STD_CCD_CACHE.with_crosslink(...).
  • Represent MVP custom chemistry as explicit RDKit-readable mapped MDL .rxn files. Portable mapped reaction representations are future/deferred and are not part of the MVP. No Python reaction plugin packages and no directory auto-discovery.
  • Normalize all moiety inputs into one Moiety artifact/model with molecule, coordinates, identities, residue definitions, charge evidence, and provenance.
  • Default force fields become ff14SB for canonical protein and Sage 2.3.0 for final connected SMIRNOFF parameterization. Users may override ordered sources explicitly.
  • Retain the current composite charge strategy: canonical protein charges, validated moiety/polymer template charges, local pre-production OpenFF NAGL junction patch (openff-gnn-am1bcc-0.1.0-rc.3.pt; not GLYCAM, CHARMM, or AshGC), reconciliation, and explicit charge templates.
  • Do not perform fragment parameter transplantation or manual Interchange surgery. Parameterize the final connected topology once using ordered OFFXML sources.
  • Coordinate mapping must use unique pdb_index/identity ledger information. Never rely on Pablo atom order because crosslinked molecules may be reordered.
  • Keep the design KISS: no registries that require core edits for data reactions, no compatibility facades, no duplicate old/new paths after parity, no broad SystemBuilder redesign, and no POC file changes.

Core contracts

Favor minimal models and delete redundant adapters once parity exists.

ContractFields and evidenceRules
Moiety OpenFF/RDKit molecule, coordinates, atom identities, residue definitions, charge evidence, source provenance. All source paths normalize here. Validate identity/order/charge count/finite values/total charge.
ResolvedReaction Selected protein site, moiety role, leaving atoms, added product bond, product residue policy, Pablo library plan. Use one canonical method, preferably resolve(...). Remove resolve_attachment versus resolve_plan drift.

Serialized reaction definitions

  • Users extend reactions through data files, not Python packages.
  • MVP input is an RDKit-readable mapped MDL .rxn file, like atrp.rxn.
  • A portable mapped reaction representation is explicitly future/deferred and must not be treated as MVP scope.
  • Configuration uses explicit paths only. There is no directory auto-discovery.
  • PolyzyMD derives linking atoms, leaving atoms, added/removed bonds, bond-order changes, and formal-charge changes from mapped reactant/product graph delta.
  • Protein versus moiety role is assigned by matching the selected protein neighborhood and the moiety graph. Ambiguous or nonmatching assignments fail.
  • Users do not configure Pablo internals.

Pablo 0.2.2 public API findings

  • Pin and test Pablo 0.2.2.
  • topology_from_pdb(...) is the loader.
  • ResidueDefinition.from_smiles, from_molecule, and from_capped_molecule create custom precursor definitions.
  • ResidueDefinition.react(...) generates product definitions from mapped SMARTS but does not modify coordinates or PDB files.
  • STD_CCD_CACHE.with_crosslink(...) derives crosslink-ready definitions retaining leaving atoms; product PDB omits leaving atoms and includes CONECT.
  • additional_definitions graph-match existing product connectivity but do not create bonds.
  • Pablo does not perform reactions, coordinate assembly, partial charging, or parameterization.
  • Pablo can reorder atoms for crosslinked molecules; use unique pdb_index/identity mapping, never order assumptions.
  • One linking_bond plus one crosslink slot per ResidueDefinition; fail clearly beyond capability.
  • Use public APIs only. Do not use private helpers such as _anon_from_smarts.

Force-field semantics and audit

Production default: retain the composite strategy: ff14SB-derived canonical protein charges + validated charged moiety/polymer templates + local pre-production OpenFF NAGL junction patch (openff-gnn-am1bcc-0.1.0-rc.3.pt; not GLYCAM, CHARMM, or AshGC) + reconciliation + explicit charge templates.
  • Project-wide defaults change to ff14SB + Sage 2.3.0. Users may override.
  • Rosemary whole-product NAGL is future/experimental only.
  • No GLYCAM support now; future validated specialized OFFXML support is possible.
  • No fragment parameter transplantation and no manual Interchange surgery.
  • Ordered OFFXML sources parameterize the final connected topology once.
  • SMIRNOFF matches graph substructures, not residue names. Later matching parameter hierarchy matters.
  • Add a small shared force-field loader/manifest/audit utility.
  • Use public ForceField.label_molecules() for assignment inspection.
  • Audit records handler, topology key/atom identities, parameter id/SMIRKS, likely source, ambiguity, and expected scope.
  • Conjugation uses strict audit. Existing SystemBuilder can share the loader with audit disabled or report-only initially.
  • Do not rewrite existing ligand/polymer/solvent charging behavior.

Branch and PR workflow

  • Create or update the integration branch conjugation-engine-refactor.
  • For each phase, create one work branch from the integration branch and open one PR back into the integration branch.
  • Use explicit staging only. Never stage unrelated dirty files, POC notebooks, temp files, test_files, or local experiment outputs.
  • Before commit, inspect git status --short, git diff, and git log --oneline -10.
  • Every semantic phase runs targeted tests, the conjugation subset, Ruff, Black, and the Phase 10 fast mixed E2E checkpoint.
  • Run the full production LipA checkpoint for high-risk gates: Pablo production switch, charge/force-field changes, major placement/identity changes, and final integration.
  • No compatibility shims. Implement parity, switch production, and delete only the old code whose complete dependency set has parity in that phase; shared/manual Pablo definition logic remains until both NHS-Lys and multi-residue polymer parity pass.
  • Each PR includes a user-review gate with checkpoint output paths and known deviations.
  • Final merge to refactor/conjugation-engine occurs only after all convergence phases pass.

Definition of done

  • The fast multi-point E2E checkpoint succeeds after every semantic phase after Phase 10; the full production LipA checkpoint succeeds for high-risk gates and final integration.
  • MVP reaction definitions are RDKit-readable mapped MDL .rxn files with explicit config paths and no Python package/plugin requirement.
  • All moiety sources normalize into the Moiety contract with strict identity, coordinate, charge, and provenance validation.
  • Public Pablo APIs ingest product topology; no private helpers are used.
  • Coordinate mapping after Pablo uses unique identity/pdb_index evidence, not atom order.
  • Composite charges remain production default and are reconciled with explicit evidence.
  • Final parameterization uses ordered OFFXML sources with ff14SB + Sage 2.3.0 defaults and concise assignment audit.
  • Old paths are deleted after complete relevant parity; no compatibility facades or duplicate production paths remain.
  • POC notebooks, temp files, unrelated dirty files, and unrelated tests are untouched.
  • Final merge to refactor/conjugation-engine is user-approved after Phase 19 audit.
